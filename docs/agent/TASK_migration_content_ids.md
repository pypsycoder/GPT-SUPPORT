## 1. Первый шаг — разведка, а не миграция

**Не пиши миграцию, пока не выяснишь, есть ли что мигрировать.** Возможно,
контент в БД ещё не импортирован, и тогда вся задача сводится к правке импортёров
и переимпорту, без Alembic вообще.

Выполни и приложи результат к отчёту:

```sql
SELECT count(*) FROM education.lessons;
SELECT id, code, topic, block_code, order_index FROM education.lessons ORDER BY order_index;

SELECT count(*) FROM education.lesson_tests;
SELECT id, lesson_id, code, title FROM education.lesson_tests ORDER BY id;
SELECT count(*) FROM education.lesson_test_questions;

SELECT count(*) FROM practices.practices;
SELECT id, module_id, type, title FROM practices.practices ORDER BY module_id, id;

-- Данные пациентов: если здесь непусто, любое изменение id практик
-- обязано сохранить связь, иначе потеряем историю выполнения
SELECT count(*) FROM practices.practice_completions;
SELECT count(*) FROM education.lesson_test_results;
SELECT count(*) FROM education.lesson_progress;
```

**Развилка по результату:**

- **Все таблицы контента пусты** → миграция схемы не нужна. Делаем только §2–§4
  (правка импортёров) и переимпорт. Отчитайся об этом и остановись перед §5.
- **Контент есть, `practice_completions` / `lesson_test_results` / `lesson_progress` пусты**
  → можно чистый переимпорт с предварительным `TRUNCATE` контентных таблиц.
  Пользовательских данных не теряем.
- **Есть пользовательские данные** → нужна миграция с сохранением связей, §5.
  Это единственный сценарий, где нужен Alembic.

## 2. Блокер: коды уроков разъедутся с кодами тестов

Это надо решить до всего остального.

`scripts/import_lesson_from_md.py` формирует код урока из **имени файла урока**:

```python
lesson_code = f"{order_from_name:02d}_{slug}"     # 01_Питание.md -> "01_pitanie"
```

`scripts/import_lesson_test_from_json.py` ищет урок по коду, собранному из
**имени файла теста**:

```python
lesson_code_base = f"{order:02d}_{slug_base}"     # 202_Питание-тест.md -> "202_pitanie"
```

Файлы тестов переименованы, файлы уроков — нет. Значит после переимпорта тест
`202_Питание-тест.md` пойдёт искать урок с кодом `202_pitanie`, а в БД он лежит
как `01_pitanie`. **Привязка теста к уроку сломается, тесты осиротеют.**

Нужно выбрать один вариант и согласовать со мной до реализации:

**Вариант А — переименовать файлы уроков** (`01_Питание.md` → `202_Питание.md`,
`01.Стресс.md` → `101.Стресс.md` и т. д.). Схема становится сквозной: номер файла =
`order` = `test_id` = номер модуля везде. Ломает существующие `lessons.code` в БД —
их придётся обновить.

**Вариант Б — оставить имена файлов уроков, развязать `order` и `code`.**
Ввести явное поле в шапке md-урока (например `<!-- module: 202 -->`) и брать номер
оттуда, а не из имени файла. Файлы не трогаем, но появляется два источника номера.

Я склоняюсь к **А** — меньше неявного, и правило «номер один и тот же везде»
проверяется автоматически. Но это твоя зона: посмотри, где ещё в коде и во фронтенде
завязано на `lessons.code` и `order_index`, и скажи, если А обойдётся дороже.

**Проверь перед решением:**

```bash
grep -rn "lessons.code\|lesson_code\|order_index" app/ frontend/ scripts/ --include=*.py --include=*.js | grep -v test
```

## 3. Практики: id генерируется из module_id — он изменился

`scripts/import_practices.py`:

```python
def make_practice_id(module_id, practice_type, raw_title) -> str:
    digits = "".join(re.findall(r"\d+", raw_title))
    if len(digits) >= 2:
        return f"p{module_id}_{practice_type}_{digits}"
    return f"p{module_id}_{practice_type}"
```

Отсюда два следствия.

**Первое: id практик изменятся сами собой.** `p01_breathing_478` станет
`p101_breathing_478`, потому что `module_id` в файле теперь `101`. А
`practices.practice_completions.practice_id` — внешний ключ на `practices.practices.id`.
Наивный переимпорт создаст дубли и осиротит историю выполнения практик.

**Второе: генерация id по содержанию заголовка — плохая идея.** Она уже даёт
неустойчивые результаты: `p02_body_54321` — это «Заземление 5-4-3-2-1», где число
из названия техники попало в идентификатор. Переименование практики меняет её id.

**Что сделать:**

1. Перевести импортёр на **явный id из заголовка блока**. В файлах он уже есть:
   `## П-201 · Питание · Поведенческая`. Парси `П-NNN` и клади в `practices.id` как есть.
   `make_practice_id()` удалить.
2. `module_id` в модели объявлен как `String`. Решить: приводить к `Integer`
   (нужна миграция типа) или оставить строкой. **Рекомендую Integer** — номер модуля
   теперь честное число, а сортировка по строке даст «101, 110, 201, 21» при росте.
   Если меняешь тип — не забудь `USING module_id::integer` и проверь, что в таблице
   нет нечисловых значений.
3. Путь по умолчанию в `import_practices.py` — `content/practice/practices_block_a.md`,
   этого файла больше нет. Читать все три файла блоков.
4. Если `practice_completions` непуста — таблица соответствия старых и новых id
   лежит в `content/practice/PRACTICE_ID_MAP.json` (поля `прежний` → `новый`).
   Прежние id в БД имеют вид `p{старый_module}_{type}[_{digits}]`, а не `П-01`,
   поэтому сопоставлять придётся по паре (title, старый module_id), а не по шифру.
   **Сначала выведи фактические id из БД и покажи мне сопоставление, прежде чем обновлять.**

## 4. Тесты: `lesson_tests.code`

`code` формируется как `f"{order:02d}_{slug_full}"` из имени файла теста, то есть
после переименования станет `101_stress-test` вместо `01_stress-test`.

Если в БД уже есть записи — это `UPDATE` по `code`, а не вставка новых. Иначе
получим два теста на один урок, а `lesson_test_results.test_id` будет указывать
на старый.

Обрати внимание: `code` объявлен `unique=True`, так что порядок операций важен —
обновлять по одному или во временную схему.

## 5. Миграция (только если §1 показал пользовательские данные)

**Правила проекта:** миграции не генерируются и не применяются без явной команды.
Команда на эту задачу дана. Порядок запуска, верификация revision и правила `stamp` —
в `ALEMBIC_RUNBOOK.md`. **Внимание: этого файла в корне репозитория сейчас нет,
хотя `CLAUDE.md` на него ссылается.** Найди его или скажи мне — не действуй по памяти.

Требования к миграции:

1. **Одна ревизия**, date-based id по принятому в проекте формату (`20260830_01_...`).
2. **Обязательный `downgrade()`**, который реально возвращает прежние значения.
   Для этого таблицу соответствия старых и новых id зашей в саму миграцию константой,
   а не читай из файла — файл может измениться.
3. **Никаких `DELETE` и `TRUNCATE` по таблицам с пользовательскими данными.**
   `practice_completions`, `lesson_test_results`, `lesson_progress` не трогаем
   иначе как обновлением ссылочных полей.
4. Перед изменением `practices.id` — либо временно снять FK, либо использовать
   `ON UPDATE CASCADE`, либо обновлять в порядке «вставить новые → перевести
   completions → удалить старые». Выбери и обоснуй в комментарии к ревизии.
5. Прогнать `alembic upgrade head` и **сразу `alembic downgrade -1` и снова `upgrade`**
   на копии базы. Если downgrade не отрабатывает — миграция не готова.
