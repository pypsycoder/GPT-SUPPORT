# Мультиагентная система на GigaChat: боевой мануал

Дмитрий, это разбор твоей ситуации в GPT-SUPPORT плюс референсная реализация.
Файлы проекта я не трогал — только читал. Весь код лежит в `ref/` отдельно.

**Главный вывод за одну строку:** твоя система платит полную цену за каждый
токен контекста, хотя GigaChat умеет отдавать префикс из кэша бесплатно —
и это лечится не сокращением промптов, а порядком сборки `messages`.

## Часть 1. Диагноз

### 1.1. Почему «как в первый раз»

Ты правильно описал симптом, но причина не в отсутствии памяти у модели.
Причина в том, что GigaChat **умеет** кэшировать контекст между запросами,
а `pool.py` этой возможностью не пользуется.

Смотри свой код, `app/llm/pool.py`:

```python
payload = {
    "model": model_name,
    "messages": [{"role": "system", "content": system_prompt}, *messages],
    "temperature": temperature,
    "max_tokens": 512,
}
```

и заголовки:

```python
headers = {
    "Authorization": f"Bearer {token}",
    "RqUID": str(uuid.uuid4()),
}
```

Нет `X-Session-ID`. Значит сервер на каждый запрос генерирует новый uuid4
сессии, и префиксный кэш никогда не срабатывает. Ты платишь полную цену
за системный промпт, профиль пациента и всю историю — на каждом из 5-7
вызовов оркестрации.

Из `AGENT_SYSTEM_ANALYSIS.md`: ~6 500 input-токенов на запрос при full
orchestration. При работающем кэше платная часть — это только дельта хода,
то есть сотни токенов, а не тысячи.

### 1.2. Почему «много правил и костылей»

Три источника, все устранимы:

**Парсинг ответа текстом.** `policy.py` разбирает ответ модели функцией
`_parse_field_block(text, required_fields)`, ловит ошибки, строит
`_build_intake_retry_instruction(previous_error)` и ретраит до `_MAX_ATTEMPTS = 3`.
Это ~300 строк инфраструктуры вокруг того, что GigaChat умеет сам через
`response_format: {"type": "json_schema", "strict": true}`.

**Классификация подстроками.** `router.py`:

```python
if any(kw in lower for kw in SAFETY_KEYWORDS):
```

Подстрочное вхождение. Ловит «покончить с этим делом» как кризис и не ловит
«больше не вижу смысла», если такой формулировки нет в списке. Каждый
пропуск чинится добавлением слова — списки растут, точность нет.

Там же, `app/llm/router.py`, отдельный баг, который стоит починить независимо
от всей миграции:

```python
def _is_emergency_vitals(text: str) -> bool:
    for val in re.findall(r'\b(\d{3,})\b|(\d{3,})(?=/)', text):
        num = val[0] or val[1]
        if num and int(num) >= 180:
            return True
```

Это ловит **любое** трёхзначное число ≥180. «Выпил 250 мл воды» — гипертонический
криз, эскалация на Max-модель и тревожный ответ пациенту с водным ограничением.
Ловить надо пару чисел, а не одно, и учитывать, что пациенты пишут давление
тремя способами: `160/100`, `160 на 100`, `160-100`. Реализация — `_BP_RE`
в `ref/router.py`, регрессионные тесты — `test_l0_no_false_crisis_on_numbers`.

**Предзагрузка контекста «на всякий случай».** `context_builder.py` собирает
витальные, расписание, прогресс, RAG — и всё это едет в промпт независимо от
того, нужно ли оно. Модель платит за данные, которые не использует.

### 1.3. Почему в браузере работает лучше

Веб-версия — это один агент с длинной сессией, инструментами и серверным
кэшем контекста. У тебя — оркестрация из шести коротких stateless-вызовов,
каждый со своим системным промптом, каждый заново оплачиваемый.

Разница не в качестве модели. Разница в архитектуре обращения к ней.

## Часть 2. Матчасть: 7 фактов о GigaChat API, меняющих архитектуру

Всё проверено по официальной документации на 09.08.2026, ссылки в конце.

### Факт 1. Есть префиксное кэширование через `X-Session-ID`

> Если при получении запроса модель находит в кэше данные о запросе с таким же
> идентификатором и частично совпадающим контекстом, то она не пересчитывает
> этот контекст.

Заголовок — произвольная строка. Если не передать, сервер подставит случайный
uuid4, то есть кэш гарантированно не сработает.

Количество взятых из кэша токенов приходит в `usage.precached_prompt_tokens`.

### Факт 2. Кэшированные токены не тарифицируются

Из OpenAPI-спецификации, поле `total_tokens`:

> Общее число токенов, подлежащих тарификации, после вычитания кэшированных
> токенов (поле `precached_prompt_tokens`).

Это не скидка 30%, это вычитание. Отсюда прямое следствие: правильная сборка
промпта — самый крупный рычаг экономии, который у тебя есть. Всё остальное
(сокращение промптов, выбор Lite вместо Pro) даёт меньше.

### Факт 3. Кэш префиксный

«Частично совпадающий контекст» означает совпадение с начала. Первое
расхождение обнуляет кэш на весь хвост. Из этого вытекает единственное
правило сборки, вокруг которого строится вся глава 4.

### Факт 4. Есть структурный вывод по JSON Schema

```json
"response_format": {
  "type": "json_schema",
  "schema": { "type": "object", "properties": {...}, "required": ["..."] },
  "strict": true
}
```

Важная деталь из документации: **без массива `required` модель вернёт
произвольный JSON, даже при `strict: true`**. Ставь `required` всегда.

Это полностью закрывает задачу `policy.py` с парсерами полей и repair-ретраями.

### Факт 5. Есть нативный function calling

`functions` (массив описаний), `function_call` (`none` / `auto` / `{"name": ...}`),
ответ приходит в `choices[0].message.function_call` + `functions_state_id`.

Жёсткий инвариант, о который легко разбиться:

> Если идентификатор взят из ответа со сгенерированными аргументами, то в
> истории сообщений нужно передать результат работы функции в сообщении с
> ролью `function`. В противном случае вернётся ошибка: «every assistant
> function call must have a result in history».

То есть в историю уходит **пара** сообщений: `assistant` с `function_call` и
`functions_state_id`, следом `function` с результатом.

### Факт 6. Жёсткие ограничения на `system`

> В запросе можно передать только один системный промпт. Системный промпт
> должен быть первым сообщением в массиве. Наличие нескольких системных
> промптов или передача не в первом сообщении приведёт к ошибке 422.

Поэтому профиль пациента и свёртку истории нельзя класть в `system`.
Решение — псевдо-диалоговая пара `user`/`assistant` сразу после системного
промпта, см. `ref/prompt_assembly.py`.

### Факт 7. Лимит потоков

> Физическим лицам доступен один поток. Юридическим лицам и ИП — 10 потоков
> по умолчанию.

Твой пул аккаунтов — обход этого лимита. Но параллельный запуск трёх
специалистов на одном аккаунте физлица не ускоряет, а сериализует с риском 429.
Плюс: разные аккаунты — разные кэши. Пул аккаунтов и префиксное кэширование
конфликтуют. Один тред пациента должен жить на одном аккаунте.

### Что ещё есть и стоит знать

- `POST /tokens/count` — точный подсчёт вместо оценки «символы / 4».
- `POST /embeddings` — модели `EmbeddingsGigaR`, `Embeddings-3B-2025-09`.
- `POST /batches` — пакетный режим для фоновых задач (переиндексация,
  массовая свёртка). Дешевле синхронных вызовов.
- `finish_reason: "blacklist"` — тематическая блокировка. Отдельная ветка
  обработки: это не ошибка сети, ретраить бессмысленно.
- Два живых базовых URL: старый `gigachat.devices.sberbank.ru/api/v1`
  и новый `api.giga.chat/v1`. Есть также `/v2/chat/completions` с другой
  формой ответа (`usage.input_tokens_details.cached_tokens` вместо
  `precached_prompt_tokens`). Мигрировать сейчас не обязательно.

## Часть 3. Целевая архитектура

### 3.1. Главное архитектурное решение

**Не мультиагентная система, а один агент с инструментами.**

Мультиагентность оправдана, когда подзадачи независимы и выполняются
параллельно на разных данных. У тебя это не так: «эмоциональный эксперт»,
«образовательный эксперт» и «composer» работают с одним и тем же контекстом
одного пациента, последовательно, и каждый платит за контекст заново.

Держи разделение агентов там, где оно даёт изоляцию, а не там, где оно
имитирует структуру команды.

Оставить как отдельные вызовы стоит только это:

| Компонент | Почему отдельно |
|---|---|
| Роутер L2 | Общий кэш префикса на всех пациентов, Lite-модель, копеечный |
| Основной агент | Единственный, кто держит контекст пациента |
| Сумматор | Фоновый, вне критического пути, Lite |
| Судья (офлайн) | Только в регрессионных прогонах, не в проде |

Убрать: composer, critic, rewrite, critic-after-rewrite, отдельные
«специалисты». Их работу делает один структурный ответ основного агента
(схема `AgentReply` в `ref/agent_loop.py` возвращает текст + safety +
кандидатов в память + next_action одним вызовом).

### 3.2. Поток одного хода

```
реплика пациента
   │
   ├─ L0 роутер (regex, 0 токенов) ──── кризис/кнопка/АД ≥180 ──► готовый маршрут
   │
   ├─ L1 роутер (kNN по эмбеддингам, 1 дешёвый вызов) ──── уверен ──► маршрут
   │
   ├─ L2 роутер (Lite + json_schema, ~60 токенов, префикс в кэше) ──► маршрут
   │
   ├─ бюджет по интенту: какие слои промпта нужны, какие инструменты дать
   │
   ├─ сборка messages по слоям стабильности  ◄── профиль + свёртка + окно
   │
   ├─ агент (Pro, functions=auto, session_id=стабильный)
   │      └─ 0-3 вызова инструментов ──► каждый следующий почти весь из кэша
   │
   ├─ финальный структурный ответ (AgentReply)
   │
   ├─ ответ пациенту
   │
   └─ фон: запись хода, memory gate, свёртка при переполнении окна
```

Вызовов на ход: 1-2 в типичном случае против нынешних 5-7.
Оплачиваемых токенов: дельта хода вместо полного контекста.

### 3.3. Состав референсной реализации

```
ref/
  gigachat_client.py   клиент: X-Session-ID, structured, functions, учёт кэша
  prompt_assembly.py   сборка messages по слоям стабильности
  memory.py            4 слоя памяти + gate записи в долгосрочную
  memory_schema.sql    DDL: thread, turn, summary, fact, chunk, call_log
  tools.py             реестр инструментов под function calling
  agent_loop.py        агентный цикл + rolling summary
  router.py            каскад L0/L1/L2
  budget.py            бюджеты по интентам, оркестратор хода, телеметрия
  test_reference.py    тесты на то, что ломается чаще всего
```

## Часть 4. Контекст и кэш — главная глава

### 4.1. Единственное правило

> `messages` собираются строго по убыванию стабильности,
> и ничто выше волатильного слоя не меняется в течение сессии.

Пять слоёв:

| # | Слой | Что там | Срок жизни |
|---|---|---|---|
| 0 | SYSTEM | Роль, границы, формат | Релиз |
| 1 | PROFILE | Устойчивые факты о пациенте | Сутки / событие |
| 2 | SUMMARY | Свёртка прошлых ходов | Раз в N ходов |
| 3 | WINDOW | Последние ходы дословно | Растёт в конце |
| 4 | VOLATILE | RAG, инструкция шага, реплика | Каждый ход |

Слой 4 всегда последний. Слой 3 только дописывается. Слои 0-2 пересобираются
редко и целиком — при пересборке кэш обнуляется осознанно.

Реализация — `PromptLayers.build()` в `ref/prompt_assembly.py`.

### 4.2. Что убивает кэш (и деньги)

Проверь эти пункты по своему `context_builder.py` — там, скорее всего, есть
как минимум три из шести:

1. **Timestamp в системном промпте.** «Сегодня 14:32» меняет префикс каждую
   минуту. Если время нужно — только в волатильном слое.
2. **`json.dumps(dict)` без `sort_keys=True`.** Порядок ключей в Python
   стабилен по вставке, а вставка зависит от логики сборки. Используй
   `canonical_json()`.
3. **RAG-контекст в системном промпте.** RAG меняется каждый ход и обнуляет
   всё, что за ним. Только в волатильный слой.
4. **`uuid` запроса внутри текста промпта.**
5. **Разные системные промпты на каждом шаге цепочки при общем `session_id`.**
   Каждый шаг сбрасывает кэш следующему. Именно это происходит сейчас:
   router, specialist, composer, critic — четыре разных системных промпта.
6. **Форматирование чисел через локаль или `round()` от float.** `36.6` и
   `36.60` — разные байты.

### 4.3. Диагностика

Логируй `precached_prompt_tokens` на каждом вызове (таблица `agent.call_log`).

```sql
SELECT date_trunc('hour', created_at) AS h,
       sum(precached_tokens)::float
         / nullif(sum(prompt_tokens + precached_tokens), 0) AS cache_hit,
       sum(total_tokens) AS billed
FROM agent.call_log
WHERE created_at > now() - interval '2 days'
GROUP BY 1 ORDER BY 1;
```

Ориентиры:

- первый ход в треде: `cache_hit` ≈ 0 — нормально;
- второй и далее: ожидай 0.5-0.8;
- стабильно около нуля — ищи нестабильный байт в префиксе;
- `prefix_fp` меняется чаще, чем ты ожидал — вот и утечка.

`prefix_fingerprint()` пишется в лог специально для этого: отпечаток
стабильной части должен быть постоянным в пределах сессии.

### 4.4. Про `session_id`

```python
def session_key(patient_id, thread_id, prefix_fingerprint) -> str:
    return f"p{patient_id}-{thread_id}-{prefix_fingerprint}"
```

Отпечаток входит в ключ намеренно. Если стабильная часть изменилась
(новый релиз промпта, обновился профиль), старый кэш всё равно бесполезен —
лучше честно начать новый, чем получить частичные совпадения и
непредсказуемый счёт.

**Конфликт с пулом аккаунтов.** Кэш живёт на стороне сервера в контуре
аккаунта. Если тред пациента прыгает между `GIGACHAT_KEY_A1` и `A2`, кэш
не переиспользуется. Нужен sticky-роутинг: `hash(thread_id) % len(accounts)`,
с переключением только при отказе аккаунта.

## Часть 5. Память

### 5.1. Четыре слоя

| Слой | Хранилище | Где в промпте | Как пишется |
|---|---|---|---|
| Working | `agent.turn` | Слой 3, дословно | Каждый ход, append-only |
| Episodic | `agent.summary` | Слой 2, абзац | Свёртка по триггеру, фоном |
| Semantic | `agent.fact` | Слой 1, key-value | Только через gate |
| Retrieval | `agent.chunk` | Слой 4, куски | Индексация офлайн |

Сырой лог ходов **никогда не идёт в промпт целиком** — он нужен для
пересборки свёрток и для разборов. В промпт идут только свёртка, факты и
хвост окна.

### 5.2. Что у тебя не так сейчас

`app/llm/memory/session.py`:

```python
class InMemorySTMemoryStore:
    def __init__(self) -> None:
        self._store: dict[tuple[int, str, str], list[dict]] = {}

st_memory_store = InMemorySTMemoryStore()
```

Память в процессе. Следствия: теряется при рестарте, не видна другому
воркеру uvicorn, не видна telegram-боту, если он отдельный процесс. При
нескольких воркерах пациент попадает то на воркер с памятью, то без.

Дизайн в `memory_schema.md` правильный. Не хватает персистентности —
DDL в `ref/memory_schema.sql`, репозиторий в `ref/memory.py`.

### 5.3. Долгосрочная память: главный риск

Долгосрочная память деградирует не от нехватки записей, а от избытка.
Через неделю бесконтрольной записи профиль пациента превращается в шум,
который едет в каждый запрос и портит ответы.

Три защиты, все реализованы в `MemoryGate`:

**Закрытый список ключей.** Ключ — `Literal[...]`, который в JSON Schema
уезжает как `enum`. При `strict: true` модель физически не сможет вернуть
ключ вне списка. Это лучше любой валидации постфактум.

**Пороги подтверждений по политикам:**

```python
POLICY_MIN_EVIDENCE = {
    "explicit_user_preference": 1,   # сказал прямо — верим сразу
    "progress_event": 1,             # объективное событие
    "repeated_pattern": 2,           # нужно повторение
    "stable_behavior_signal": 3,     # нужна устойчивость
}
```

До достижения порога кандидат копится в `evidence_count`, но не считается
боевым фактом.

**TTL по типу ключа.** Предпочтение по стилю ответа — бессрочно.
`current_life_circumstance` — 30 дней. Всё, что описывает «сейчас»,
обязано протухать, иначе через полгода агент будет уверен, что у пациента
до сих пор ремонт в квартире.

**Решение о записи принимает детерминированный код, не модель.** Модель
только предлагает кандидатов в поле `memory_candidates` структурного ответа.
Это ноль дополнительных вызовов и полный контроль над тем, что оседает
в профиле.

### 5.4. Свёртка истории

```python
async def summarize(client, previous_summary, evicted, model="GigaChat-2")
```

Rolling summary: старая свёртка + вытесненные ходы → новая свёртка.
Триггер двойной (объём и число ходов) — см. `CompactionPolicy`.

Три правила, которые экономят нервы:

- **Свёртка фоновая.** Пациент не ждёт. `BackgroundTasks` или воркер.
- **Lite-модель.** Свёртка — простая задача, Pro тут не нужен.
- **Версия сумматора в БД.** `summarizer_version` + диапазон `seq_from..seq_to`
  позволяют пересчитать старые свёртки при смене промпта, не теряя историю.

Оставлять после свёртки 2 хода — плохо, модель теряет нить. 4-6 — рабочий
компромисс.

## Часть 6. Структурный вывод вместо парсеров

Что уходит из `policy.py`:

```
_strip_code_fence, _parse_field_block, _build_intake_retry_instruction,
_build_delegation_retry_instruction, _build_expert_retry_instruction,
parse_intake_card, validate_intake_card, parse_delegation_card,
validate_delegation_card, parse_emotional_expert_card, ...
```

Что приходит вместо:

```python
class AgentReply(BaseModel):
    reply: str = Field(max_length=1500)
    safety: SafetyFlag
    memory_candidates: list[dict] = Field(default_factory=list, max_length=3)
    next_action: str | None = Field(default=None, max_length=80)

reply, comp = await client.structured(messages, AgentReply, session_id=sid)
```

Три подводных камня:

1. **`$ref` ломает strict.** Pydantic для вложенных моделей генерирует
   `$defs` + `$ref`. Функция `json_schema_for()` инлайнит их. Держи схемы
   плоскими — это ещё и дешевле по токенам.
2. **Без `required` схема не соблюдается.** Прямо сказано в документации.
   `json_schema_for()` это обеспечивает через Pydantic.
3. **Не смешивай `functions` и `response_format` в одном запросе.**
   Поведение непредсказуемо. В `agent_loop.py` это разведено на две фазы:
   сбор данных инструментами → отдельный структурный финал. Второй вызов
   почти бесплатный, потому что весь префикс уже в кэше.

Одну repair-попытку в `structured()` я оставил — на краевые схемы. При
`strict: true` она срабатывает редко, но пусть будет.

## Часть 7. Инструменты вместо специалистов

### 7.1. Когда это выигрывает

Сейчас `context_builder.py` тянет витальные, расписание, прогресс и RAG
заранее — модель платит за них всегда. С функциями модель просит только то,
что нужно.

Цена: +1 round-trip на вызов инструмента. Выигрыш появляется, когда
инструмент нужен реже, чем в половине запросов. **Меряй, а не верь на слово.**
Если `get_recent_vitals` нужен в 80% диалогов — дешевле грузить заранее.

### 7.2. Правило про количество

Описания функций едут в каждый запрос и стоят токенов. Давай модели только
инструменты, релевантные интенту — это работа роутера:

```python
TOOLS_BY_INTENT = {
    Intent.EMOTIONAL: [],                                    # разговор, без баз
    Intent.CLINICAL:  ["get_recent_vitals", "get_dialysis_schedule"],
    Intent.EDUCATION: ["search_education"],
    Intent.SAFETY:    [],                                    # отвечаем сразу
}
```

12 функций в промпте — не только дорого, но и заметно снижает точность выбора.

### 7.3. Инварианты цикла

```python
messages.append({
    "role": "assistant",
    "content": "",
    "function_call": {"name": fc.name, "arguments": fc.arguments},
    "functions_state_id": comp.functions_state_id,
})
messages.append({"role": "function", "content": result})
```

Оба сообщения, в этом порядке. Иначе 422.

Ошибки инструментов **не поднимаются наверх**, а возвращаются модели как
данные:

```python
return json.dumps({"error": "tool_failed", "detail": str(exc)[:200]})
```

Падение цикла из-за кривого аргумента — худший сценарий в проде. Пусть
модель увидит ошибку и решит, что делать.

Потолок 3 хопа. Выше — почти всегда зацикливание, а не польза.

## Часть 8. Роутер

Каскад: каждый следующий уровень дороже и вызывается, только если
предыдущий не дал уверенного ответа.

| Уровень | Механика | Цена | Покрытие |
|---|---|---|---|
| L0 | regex, детерминированные сигналы | 0 | кнопки, АД, кризисные фразы |
| L1 | kNN по эмбеддингам прототипов | 1 embeddings-вызов | ~90% текста |
| L2 | Lite + json_schema, общий session_id | ~60 токенов | остаток |

**Про безопасность.** Списки стоп-слов остаются, но работают **только на
повышение приоритета**, никогда на понижение. Ложноположительный SAFETY
стоит одного лишнего аккуратного ответа. Ложноотрицательный — несопоставимо
дороже. Отсюда же строчка в промпте L2: «при сомнении между safety и любым
другим интентом выбирай safety».

**Про L1.** Прототипы — 15-30 размеченных примеров на интент, эмбеддятся
один раз при старте. Расширение — добавлением примеров из реальных логов,
а не правкой регулярок. Два порога:

- `threshold=0.62` — ниже не доверяем;
- `margin=0.05` — если два интента слишком близко, отдаём на L2.

Начальный набор в `SEED_PROTOTYPES`. Первые же 200 реальных диалогов дадут
материал для нормального набора.

**Про L2.** Системный промпт константен → при общем `session_id="router-shared"`
он уходит в кэш для всех пациентов. Реальная стоимость — десятки токенов.

## Часть 9. Бюджет и телеметрия

### 9.1. Бюджет задаётся в токенах и по интенту

Не «сколько влезет в контекст», а «сколько мы готовы платить за этот ход».
Контекст Pro большой, поэтому промпт распухает незаметно: ошибки переполнения
нет, есть только счёт в конце месяца.

```python
BUDGET_BY_INTENT = {
    Intent.SMALLTALK: Budget(profile=0, summary=100, window=300, retrieval=0, output=150),
    Intent.EMOTIONAL: Budget(retrieval=0, window=1600, output=600),
    Intent.EDUCATION: Budget(summary=200, window=600, retrieval=1200, output=800),
    Intent.SAFETY:    Budget(profile=400, summary=600, window=2000, retrieval=400, output=900),
}
```

Логика: эмоциональной поддержке нужна история и не нужен RAG; обучению
наоборот. Кризис — единственное место, где не экономим.

Цифры — стартовая точка, не истина. Калибруй по p95 фактического расхода
на слой из `agent.call_log`.

### 9.2. Метрики, которые надо смотреть

| Метрика | Норма | О чём говорит |
|---|---|---|
| `cache_hit_ratio` со 2-го хода | 0.5-0.8 | Работает ли префикс |
| Оплачиваемых токенов на ход | падение в 3-5× | Итоговый эффект |
| Вызовов LLM на ход | 1-2 | Не разрослась ли цепочка |
| Доля L2-роутинга | < 15% | Достаточно ли прототипов |
| Хопов инструментов | среднее < 0.5 | Не злоупотребляет ли модель |
| `finish_reason='blacklist'` | ~0 | Не триггерим ли фильтры |
| Repair-ретраев `structured` | < 2% | Не сломана ли схема |

Без `agent.call_log` разговор об оптимизации — гадание.

## Часть 11. План миграции

Порядок важен: каждый шаг измерим и не ломает предыдущий.
Ничего не трогаем в `app/` до шага 1 — сначала телеметрия.

### Шаг 0. Измерить текущее (полдня)

Создать `agent.call_log`, писать туда каждый вызов из `pool.py`.
Собрать за 2-3 дня базовую линию: токенов на ход, вызовов на ход, латентность.
**Без базовой линии нельзя доказать, что стало лучше.**

### Шаг 1. Включить кэш (1 день, максимальный эффект)

Добавить `X-Session-ID` в `pool.py`, ключ — `f"p{patient_id}-{thread_id}"`.
Sticky-роутинг тредов по аккаунтам.
Ожидание: `cache_hit` вырастет с 0 до чего-то, даже без перестройки промптов.

Это единственный шаг, который даёт эффект без рефакторинга. Сделай его первым.

### Шаг 2. Пересобрать промпт по слоям (2-3 дня)

Взять `PromptLayers`, перенести туда сборку из `context_builder.py`.
Вынести RAG и timestamp из системного промпта в волатильный слой.
Логировать `prefix_fp`.
Ожидание: `cache_hit` 0.5-0.8 со второго хода.

### Шаг 3. Структурный вывод (2-3 дня)

Заменить `_parse_field_block` и retry-инструкции на `client.structured()`.
Удалить из `policy.py` парсеры и repair-ветки.
Ожидание: минус ~300 строк, минус 10-15% вызовов (repair больше не нужен).

### Шаг 4. Схлопнуть оркестрацию (3-5 дней, самый рискованный)

Один агент с `AgentReply` вместо router→specialists→composer→critic.
Запускать параллельно со старой веткой на золотом наборе, сравнивать
по трём уровням проверки из части 10.
Переключать только после того, как метрики качества не хуже.

### Шаг 5. Персистентная память (3-4 дня)

`memory_schema.sql`, `MemoryStore`, `MemoryGate`.
Убрать `InMemorySTMemoryStore`.
Свёртка в фоне.

### Шаг 6. Каскадный роутер (2-3 дня)

L0 из существующих регулярок, L1 на прототипах из логов, L2 на Lite.
Замерить долю L2 — если выше 15%, добавить прототипов.

### Шаг 7. Инструменты (по одному)

Начать с `search_education` — он реже всего нужен, значит выигрыш очевиднее.
Мерить долю вызовов. Если инструмент вызывается чаще, чем в половине
диалогов — вернуть его в предзагрузку.

**Что удалить в конце:** composer, critic, rewrite, specialists,
`domain_scorer.py`, большую часть `keywords.py`, парсеры из `policy.py`.
Ориентировочно 2000+ строк.

## Часть 12. Что проверить экспериментально

Здесь я не уверен, и проверять надо на твоём аккаунте. Не принимай на веру.

1. **Время жизни кэша.** Документация говорит «в течение некоторого времени»,
   конкретики нет. Проверь: одинаковый запрос с одним `session_id` через
   1, 5, 30, 120 минут — смотри `precached_prompt_tokens`. От этого зависит,
   имеет ли смысл «прогревать» кэш перед прогнозируемым обращением.

2. **Гранулярность кэша.** Работает ли он на уровне сообщений или блоков
   токенов. Проверь: измени последний символ последнего сообщения окна —
   сколько токенов останется в кэше. Это скажет, насколько агрессивно можно
   дописывать в конец.

3. **Кэшируются ли описания функций.** В спецификации сказано, что кэш
   покрывает «историю сообщений массива `messages`, описание функций».
   Проверь на практике: если да, менять набор инструментов между ходами
   одного треда дороже, чем кажется, и стоит держать набор фиксированным
   на тред, а не на ход.

4. **Устойчивость `strict: true` на вложенных схемах.** Мой `json_schema_for`
   инлайнит `$defs` профилактически. Проверь, нужна ли эта предосторожность
   для твоих схем — возможно, вложенность работает.

5. **`/v2/chat/completions`.** Другая форма usage
   (`input_tokens_details.cached_tokens`). Возможно, там кэш работает иначе
   или лучше. Стоит сравнить на одном сценарии.

6. **Реальная выгода функций против предзагрузки.** Считай на своих логах
   частоту, с которой нужны витальные и расписание. Гипотеза «функции
   дешевле» может не подтвердиться для клинического интента.

7. **Точность L1 на твоих данных.** Порог 0.62 взят с потолка. Правильное
   значение — из ROC по размеченным примерам.

## Часть 13. Ограничения и риски

**Клиническая безопасность.** Схлопывание critic в один вызов убирает
второй проход по ответу. Компенсация — детерминированные ассерты на
запрещённые формулировки после генерации (не LLM-проверка, а regex/список
по вашему протоколу) и обязательное поле `safety` в схеме. Для SAFETY-ветки
я бы оставил старую логику до тех пор, пока не наберётся статистика.
Это тот случай, где экономия неуместна.

**ПДн.** `X-Session-ID` — произвольная строка, которая уходит на сервер
Сбера и логируется. Не клади туда ничего идентифицирующего: `p{patient_id}`
— это внутренний id, а не ФИО и не номер карты. Проверь по вашей модели
угроз, допустим ли даже внутренний id.

**Персистентность кэша.** Кэш на стороне провайдера, гарантий нет. Система
должна работать корректно при `cache_hit = 0` — просто дороже. Не строй
логику, которая ломается без кэша.

**Что здесь не покрыто:** стриминг (для TG-бота может быть важен для
ощущения отзывчивости), пакетный режим `/batches` для переиндексации,
миграция на `/v2`, гибридный поиск BM25+вектор в деталях.
