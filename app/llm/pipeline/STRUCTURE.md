# Current LLM Pipeline

Этот файл описывает актуальный runtime после удаления legacy-веток и adapter-слоя.

## Точки входа

- `app/routers/chat.py`
- `app/researchers/router.py`
- `app/llm/proactive.py`

Во всех трёх местах запросы теперь идут напрямую в `LLMPipeline.process(LLMRequest)`.

## Входной контракт

`LLMRequest` содержит только текущие runtime-поля:

- `patient_id`
- `user_input`
- `source`
- `supervisor_state`
- `router_result`
- `strict_model_tier`
- `db`

## Основной pipeline

Порядок стадий фиксированный:

1. `boundary_guard`
2. `classification`
3. `supervisor`
4. `memory_write`

### 1. `boundary_guard`

- режет prompt-injection и служебные запросы;
- L0 (`app/llm/router_l0.py`) детерминированно ловит кризис/острое медицинское
  состояние и может завершить pipeline через `early_response`.

### 2. `classification`

- определяет `request_type`, `model_tier`, `domain_hint` (каскад L0→L1→L2,
  см. `app/llm/router_cascade.py`);
- инициализирует `supervisor_state`.

### 3. `supervisor`

- один структурный вызов агента (`app/llm/agent/loop.py`, `Agent.run()`)
  вместо цепочки intake → delegation → expert;
- модель возвращает плоскую карточку `AgentReply` (текст + intent, safety,
  technique_id, memory_candidates) одним вызовом;
- второй эшелон защиты (`_apply_agent_safety_net`) перекрывает ответ протоколом,
  если агент сам поднял `safety_level=urgent`;
- строит финальный `response_draft`, обновляет `supervisor_state`, пишет
  диагностику хода.

### 4. `memory_write`

- нормализует memory-диагностику;
- сохраняет кандидатов в устойчивую память из `AgentReply.memory_candidates`.

## Выходной контракт

`LLMResponse` собирается напрямую из:

- `early_response` из `boundary_guard`, либо
- `response_draft` из `supervisor`.

В ответе сохраняются:

- текст ответа;
- токены и модель;
- `supervisor_state` и `supervisor_state_delta`;
- полная `diagnostics`.

## Что удалено

- `app/llm/agent.py`
- `app/llm/agent_v2.py`
- legacy stages: `context`, `intake`, `orchestration`, `validation`
- dict-adapter между runtime и API-слоем
- `app/llm/langgraph_supervisor/` (Graph v2: intake → delegation → expert) —
  заменена одноагентной веткой выше, флаг `LLM_SINGLE_AGENT` убран за
  ненадобностью (единственная ветка теперь всегда активна)
- флаги поэтапного включения каскада на GigaChat (`LLM_ROUTER_L0/L1/L2`,
  `LLM_AGENT_TOOLS`, `LLM_PROMPT_LAYERS`, `LLM_STRUCTURED_OUTPUT`) и старые
  ветки, которые они прикрывали (подстрочный поиск кризиса в `boundary_guard`,
  предзагрузка RAG вместо инструмента) — раскатка завершена, каскад,
  инструменты, послойный промпт и structured output всегда активны

## Обоснование архитектуры

Раздел собран из дизайн-спеки миграции на GigaChat (`00_MANUAL.md`, август
2026; удалена из репозитория после раскатки каскада), на которую код в
`app/llm/` ссылался по номерам частей. Здесь оставлены только факты и
правила, объясняющие форму текущего кода.

### GigaChat API — что определяет архитектуру

Проверено по документации на 09.08.2026 (ссылки в конце файла).

1. **Префиксное кэширование через заголовок `X-Session-ID`.** Сервер
   переиспользует посчитанный контекст, если запрос приходит с тем же id и
   *начало* `messages` байт-в-байт совпадает с предыдущим. Заголовок —
   произвольная строка; не передашь — сервер подставит случайный uuid4, и
   кэш гарантированно не сработает. Взятые из кэша токены приходят в
   `usage.precached_prompt_tokens`.
2. **Кэшированные токены не тарифицируются** — это вычитание из
   `total_tokens`, не скидка. Правильная сборка промпта — самый крупный
   рычаг экономии; сокращение промптов и выбор Lite вместо Pro дают меньше.
3. **Кэш префиксный.** Первое же расхождение обнуляет кэш на весь хвост.
   Отсюда единственное правило сборки (ниже).
4. **Структурный вывод по JSON Schema**
   (`response_format: {type: json_schema, strict: true}`). Без массива
   `required` модель вернёт произвольный JSON даже при `strict: true` —
   `required` ставим всегда. Закрывает задачу текстовых парсеров.
5. **Нативный function calling.** Инвариант: если `functions_state_id` взят
   из ответа со сгенерированными аргументами, в историю уходит **пара**
   сообщений — `assistant` с `function_call` + `functions_state_id`, следом
   `function` с результатом. Иначе ошибка «every assistant function call
   must have a result in history» (422).
6. **Только один системный промпт, только первым сообщением** — иначе 422.
   Профиль пациента и свёртку истории в `system` класть нельзя; решение —
   псевдо-диалоговая пара `user`/`assistant` сразу после системного промпта.
7. **Лимит потоков: 1 для физлиц, 10 для юрлиц/ИП.** Пул аккаунтов обходит
   лимит, но разные аккаунты — разные кэши. Один тред пациента должен жить
   на одном аккаунте (sticky-роутинг), иначе префиксный кэш не
   переиспользуется.

Ещё полезное: `POST /tokens/count` (точный подсчёт), `POST /embeddings`
(`EmbeddingsGigaR`), `POST /batches` (пакетный режим для фоновых задач),
`finish_reason: "blacklist"` — тематическая блокировка, ретраить бессмысленно.

### Контекст и кэш

**Единственное правило:** `messages` собираются строго по убыванию
стабильности, и ничто выше волатильного слоя не меняется в течение сессии.

| # | Слой | Что там | Срок жизни |
|---|---|---|---|
| 0 | SYSTEM | роль, границы, формат | релиз |
| 1 | PROFILE | устойчивые факты о пациенте | сутки / событие |
| 2 | SUMMARY | свёртка прошлых ходов | раз в N ходов |
| 3 | WINDOW | последние ходы дословно | растёт в конце |
| 4 | VOLATILE | RAG, инструкция шага, реплика пациента, repair-инструкция | каждый ход |

Слой 4 всегда последний, слой 3 только дописывается, слои 0–2
пересобираются редко и целиком (кэш обнуляется осознанно). Реализация —
`app/llm/prompt_assembly.py`.

**Что убивает кэш:** timestamp в системном промпте; `json.dumps` без
`sort_keys`; RAG-контекст выше волатильного слоя; uuid запроса внутри
текста; разные системные промпты на шагах цепочки при общем `session_id`;
форматирование чисел через локаль или `round()` от float (`36.6` ≠ `36.60`
по байтам).

**Ключ сессии:** `f"p{patient_id}-{thread_id}-{prefix_fingerprint}"`.
Отпечаток стабильной части входит намеренно — при смене релиза промпта или
профиля старый кэш всё равно бесполезен, честнее начать новый. Диагностика:
`precached_prompt_tokens` на каждом вызове; со 2-го хода в треде ждём
`cache_hit` 0.5–0.8, стабильный ноль → ищи нестабильный байт в префиксе.

### Память

Четыре слоя, сырой лог ходов никогда не идёт в промпт целиком:

| Слой | Хранилище | Где в промпте | Как пишется |
|---|---|---|---|
| Working | `llm.chat_messages` | слой 3, дословно | каждый ход, append-only |
| Episodic | `llm.chat_summaries` | слой 2, абзац | свёртка по триггеру, фоном |
| Semantic | `llm.patient_facts` | слой 1, факты | только через gate |
| Retrieval | RAG-чанки уроков | слой 4, куски | индексация офлайн |

**Главный риск долгосрочной памяти — не нехватка записей, а избыток:**
неконтролируемая запись за недели превращает профиль в шум, который едет в
каждый запрос. Защиты (код в `app/llm/memory_store.py`):

- решение о записи принимает детерминированный код, не модель — модель
  только предлагает кандидатов в `AgentReply.memory_candidates`;
- порог подтверждений `PROMOTION_MIN_EVIDENCE = 2` — факт активируется
  только со второго упоминания в другом ходу;
- TTL `FACT_TTL_DAYS = 45` (sliding) — всё, что описывает «сейчас», обязано
  протухать;
- потолок `MAX_ACTIVE_FACTS = 20` на пациента.

**Свёртка** (`maybe_compact`): rolling summary (старая свёртка + вытесненные
ходы → новая), фоновая, на Lite-модели, оставляет 4–6 последних ходов в окне.

### Инструменты

Function calling вместо предзагрузки всего контекста «на всякий случай».
Цена — +1 round-trip на вызов; выигрыш появляется, когда инструмент нужен
реже, чем в половине запросов (`education` — ~17% размеченных сообщений,
поэтому `search_education` под функцией; витальные при клиническом интенте
нужны почти всегда — дешевле грузить заранее).

Инварианты цикла (`app/llm/tools.py`, `app/llm/agent/loop.py`):

- пара сообщений `assistant(function_call)` + `function(result)` в этом
  порядке, иначе 422;
- ошибки инструмента не поднимаются наверх, а возвращаются модели как
  данные (`{"error": ...}`) — падение цикла из-за кривого аргумента худший
  сценарий в проде;
- потолок 3 хопа — выше почти всегда зацикливание;
- набор инструментов по интенту (`TOOLS_BY_INTENT`), не все сразу —
  описания едут в каждый запрос и стоят токенов и точности выбора.

### Роутер

Каскад, каждый следующий уровень дороже и вызывается только если предыдущий
не дал уверенного ответа:

| Уровень | Механика | Цена | Покрытие |
|---|---|---|---|
| L0 | regex, детерминированные сигналы | 0 | кнопки, АД, кризисные фразы |
| L1 | kNN по эмбеддингам прототипов | 1 embeddings-вызов | ~90% текста |
| L2 | Lite + json_schema, общий `session_id="router-shared"` | ~60 токенов | остаток |

**Безопасность:** стоп-слова работают только на повышение приоритета,
никогда на понижение. Ложноположительный SAFETY стоит одного лишнего
аккуратного ответа, ложноотрицательный — несопоставимо дороже. L1/L2
никогда не присваивают safety сами — это исключительно L0.

**L1:** прототипы — 15–30 размеченных примеров на интент из
`LLM_test/cases/intent_labels.json`, эмбеддятся один раз при старте,
расширяются добавлением примеров из логов, а не правкой регулярок. Пороги:
`threshold` (ниже — не доверяем) и `margin` (два близких интента отдаём на L2).

**L2:** системный промпт константен → при общем `session_id` уходит в кэш
один раз для всех пациентов. Схема — одно обязательное поле (лишнее поле
роняет карточку на грани, тот же замер, что у `AgentReply`).

**Почему каскад вообще:** старый `router.classify_request` (совпадение по
подстроке) на 104 размеченных сообщениях пропустил единственный настоящий
кризис и ложно пометил SAFETY «давление 200 на 100». Списки стоп-слов
росли, точность — нет. Размеченный `intent` (с обоснованием-rationale) в
`intent_labels.json` — независимая оценка человека для критики роутера, в
отличие от `router_request_type`, который просто снимок вывода старого
роутера на момент разметки.

### Ограничения и риски

- **Клиническая безопасность.** Одноагентная ветка убрала второй проход по
  ответу (critic). Компенсация — детерминированные ассерты на запрещённые
  формулировки + обязательное поле `safety` в схеме + второй эшелон
  `_apply_agent_safety_net`, перекрывающий ответ протоколом при
  `safety_level=urgent`.
- **ПДн.** `X-Session-ID` уходит на сервер Сбера и логируется. Внутри
  только `p{patient_id}` — внутренний id, не ФИО и не номер карты.
- **Персистентность кэша не гарантирована.** Система обязана работать
  корректно при `cache_hit = 0` — просто дороже. Не строй логику, которая
  ломается без кэша.

### Известные ограничения текущей ветки

Открытые вопросы с ручного прогона (август 2026), ещё не закрытые:

1. **Непрерывность техники после «Спасибо, помогло» не подтверждена
   вживую.** У `AgentReply` нет полей вроде
   `last_expert_effectiveness`/`last_expert_strategy`, которые были в
   старой ветке — `state_delta` не показывает явного закрытия техники.
   Требует решения: чинить как баг или оставить как архитектурное упрощение.
2. **`llm.llm_request_logs.account_id` — VARCHAR(20).** `boundary_guard`
   пишет туда `early_response_source.upper()`, значение обрезается до 20
   символов в `pipeline.py`. «Нормальный» фикс — расширить колонку
   миграцией (не сделано: миграции только по явному запросу).
3. **L2 иногда ошибается на не-safety классах** на коротких эмоционально
   окрашенных фразах («Как я себя чувствую» → clinical вместо emotional).
   Не баг, но точность L2 здесь стоит держать в поле зрения.
4. **Путь memory-кандидатов не подтверждён вживую** — модель ни разу не
   предложила кандидата ни в одном прогоне, только юнит-тесты. План считает
   это допустимым (поведение на усмотрение модели).
